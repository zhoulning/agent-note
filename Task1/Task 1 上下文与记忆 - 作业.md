## 实验 2-9：Agent 状态栏 / System Hint
### 运行说明
项目：`chapter2/system-hint`  
运行方式：`python main.py --mode preview`（完全离线，不调用 API）  
运行时间：2026-09-19  
证据目录：`Task1/实验2-9执行结果/system-hint-preview`

### 实验目的
理解「上下文如何被组织」：Agent 框架不只是把对话消息拼起来，还可以把**隐式状态**提炼成**显式状态栏**，以一条 `role=user` 消息追加到上下文末尾，让模型在下一次生成时看到。

### 实验结果
离线预览对比了 5 种状态栏技术：

| 技术 | 无状态栏 | 有状态栏 | 作用 |
| --- | --- | --- | --- |
| 时间戳 | 消息无时间 | `[2025-09-14 10:30:45]` | 理解「昨天 / 今天」时序 |
| 工具计数器 | 不知道调了几次 | `[Tool call #3 for 'phone_call']` | 防止无限重复调用 |
| TODO 列表 | 模型需自己回忆进度 | 显示 3 条任务及状态 | 外部记忆，保持任务连贯 |
| 详细错误 | 只有 `File not found` | 错误类型 + 参数 + 修复建议 | 从盲目重试变成分析性修复 |
| 系统状态 | 不知道自己在哪 | 时间、目录、OS、Shell、Python | 做出平台相关决策 |

实际追加到上下文末尾的状态栏示例：
```text
=== SYSTEM STATE ===
Current Time: 2025-09-14 10:30:45
Current Directory: ...
System: Windows (10)
Shell Environment: Windows Command Prompt or PowerShell
Python Version: 3.11.2

=== CURRENT TASKS ===
TODO List:
  [1] ✅ 拨打 Xfinity 客服核实退款政策 (completed)
  [2] 🔄 提交退款申请 (in_progress)
  [3] ⏳ 确认退款到账 (pending)
```

### 关键理解：上下文是怎么组织的
1. **静态前缀**：system prompt + 工具定义（通常不变）
2. **动态轨迹**：user / assistant / tool 消息（随交互增长）
3. **状态栏（system hint）**：框架自动追加到末尾的 `role=user` 消息
4. 状态栏放在**最末尾**，紧邻模型即将生成的 token，因此注意力权重高
5. 状态栏是「追加」而不是「修改」，所以前面已缓存的 KV Cache 不受影响

### 结论
上下文不是简单地把聊天记录堆进去。好的 Agent 框架会把**时间、工具调用次数、任务进度、错误诊断、环境状态**等隐式信息，组织成显式状态栏注入上下文。这直接决定了模型「能看到什么」，也就决定了它「能做出什么决策」。

## 实验 3-5：BM25 稀疏检索与 RAG
### 运行说明
项目：`chapter3/sparse-embedding`  
运行方式：`python cli.py ...`（完全离线，仅 Python 标准库）  
运行时间：2026-09-19  
证据目录：`Task1/实验3-5执行结果/bm25-cli`

### 实验目的
理解 RAG 中最基础的检索环节：BM25 如何用倒排索引 + TF/IDF 打分，从语料中找出与查询相关的文档。

### 实验结果
#### 1. 检索质量评测（默认参数 k1=1.5, b=0.75）
| 查询 | recall@5 | precision@5 | 备注 |
| --- | ---: | ---: | --- |
| model distillation | 1.00 | 1.00 | 正常召回 |
| HTTP 404 error | 1.00 | 0.50 | 召回正确，但混入无关文档 |
| XK9-2B4-7Q1 | 1.00 | 1.00 | 编号精确匹配 |
| BM25 ranking function | 1.00 | 1.00 | 正常召回 |
| cat | 0.00 | 0.00 | **完全漏召回** |

宏平均：
```text
recall@5 = 0.800
precision@5 = 0.700
MRR = 0.800
```

#### 2. 单条查询 + 逐词打分（model distillation）
| 排名 | 文档 | 分数 | 命中词 |
| --- | --- | ---: | --- |
| 1 | doc_3 Model Distillation | 3.1216 | model, distillation |
| 2 | doc_4 Knowledge Distillation | 2.2197 | model, distillation |

逐词贡献示例（doc_3）：
```text
'model':        TF=3, 文档长度=13词, IDF=1.2238, BM25贡献=1.9705
'distillation': TF=1, 文档长度=13词, IDF=1.2238, BM25贡献=1.1511
```

这说明：TF 越高、词越稀有（IDF 越高），对排序贡献越大。

#### 3. 扩展：修改 BM25 参数对比
| 参数 | doc_3 分数 | doc_4 分数 | 分数差 |
| --- | ---: | ---: | ---: |
| 默认 k1=1.5, b=0.75 | 3.1216 | 2.2197 | 0.9019 |
| k1=2.0, b=0.5 | 3.3117 | 2.2746 | 1.0371 |
| k1=1.0, b=0.0 | 3.0594 | 2.4476 | 0.6118 |

参数含义与观察：
- **k1（词频饱和）**：调大后，高词频文档得分更高，分数差拉开
- **b（文档长度归一化）**：调小后，长短文档差异被弱化，doc_4（更长）相对追近
- **b=0**：完全不做长度归一化，长文档不再被惩罚

评测指标层面：在这套小语料上，改参数没有改变 recall@5（仍为 0.800），因为「cat」的失败来自**同义词缺失**，不是排序参数问题。

#### 4. 同义词短板（cat）
查询 `cat`，相关文档是 doc_7 / doc_8（讲 kitten / feline），但 BM25 完全命中不了：
```text
没有命中任何文档（所有查询词都不在倒排索引中）。
```

这是**词法匹配**检索的根本局限：查询词和文档词没有字面重叠，就召回不了。

### 结论
1. **RAG 的检索层**负责「从知识库里捞出和问题相关的片段」，BM25 是最经典的稀疏检索方法。
2. BM25 基于词面匹配（TF/IDF/文档长度），**能解释、能调参、速度快**。
3. 参数 k1 / b 会改变分数和排序，但解决不了**语义鸿沟**（同义词、近义表达）。
4. 这正是后续需要**稠密向量检索 / 混合检索 / 重排序**的原因。

## 综合总结：短期上下文 vs 长期记忆 vs RAG
| 概念 | 存在哪里 | 生命周期 | 实验对应 |
| --- | --- | --- | --- |
| **短期上下文** | 每次 LLM 调用的消息列表 | 当前会话内 | 实验 2-9 状态栏 |
| **长期记忆** | 跨会话存储（用户偏好、历史事实） | 持久化 | 第 3 章 user-memory |
| **RAG 知识库** | 外部文档库 / 向量索引 | 持久化，按需检索 | 实验 3-5 BM25 |

一句话关系：
```text
短期上下文 = 这次模型「看得见」的信息
长期记忆  = 跨会话「记得住」的信息
RAG       = 从外部知识库「捞回来」再塞进上下文的信息
```

实验 2-9 说明：上下文是被**组织**出来的，不是简单堆叠。  
实验 3-5 说明：RAG 是把外部知识**检索进上下文**的关键管道；检索质量直接决定 Agent 能否基于正确知识作答。
