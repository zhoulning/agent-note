## 实验 2-9：Agent 状态栏 / System Hint（本人运行）

### 运行说明

项目：`chapter2/system-hint`  
运行方式：`python main.py --mode preview`（完全离线，不调用 API）  
运行时间：2026-09-19  
证据目录：`Task 1 上下文工程/实验2-9执行结果/system-hint-preview`

### 实验目的

理解「上下文如何被组织」：Agent 框架不只是把对话消息拼起来，还可以把**隐式状态**提炼成**显式状态栏**，以一条 `role=user` 消息追加到上下文末尾，让模型在下一次生成时看到。

### 实验结果

离线预览对比了 5 种状态栏技术：

| 技术 | 无状态栏 | 有状态栏 | 作用 |
| --- | --- | --- | --- |
| 时间戳 | 消息无时间 | `[2025-09-14 10:30:45]` | 理解「昨天 / 今天」时序 |
| 工具计数器 | 不知道调了几次 | `[Tool call #3 for 'phone_call']` | 防止无限重复调用 |
| TODO 列表 | 模型需自己回忆进度 | 显示 3 条任务及状态 | 外部记忆，保持任务连贯 |
| 详细错误 | 只有 `File not found` | 错误类型 + 参数 + 修复建议 | 从盲目重试变成分析性修复 |
| 系统状态 | 不知道自己在哪 | 时间、目录、OS、Shell、Python | 做出平台相关决策 |

实际追加到上下文末尾的状态栏示例：

```text
=== SYSTEM STATE ===
Current Time: 2025-09-14 10:30:45
Current Directory: ...
System: Windows (10)
Shell Environment: Windows Command Prompt or PowerShell
Python Version: 3.11.2

=== CURRENT TASKS ===
TODO List:
  [1] ✅ 拨打 Xfinity 客服核实退款政策 (completed)
  [2] 🔄 提交退款申请 (in_progress)
  [3] ⏳ 确认退款到账 (pending)
```

### 关键理解：上下文是怎么组织的

1. **静态前缀**：system prompt + 工具定义（通常不变）
2. **动态轨迹**：user / assistant / tool 消息（随交互增长）
3. **状态栏（system hint）**：框架自动追加到末尾的 `role=user` 消息
4. 状态栏放在**最末尾**，紧邻模型即将生成的 token，因此注意力权重高
5. 状态栏是「追加」而不是「修改」，所以前面已缓存的 KV Cache 不受影响

### 扩展对比：开 / 关状态栏的差异

| 对比项 | 无状态栏 | 有状态栏 |
| --- | --- | --- |
| 时序理解 | 分不清昨天/今天 | 时间戳明确 |
| 工具重复风险 | 高（不知道调了几次） | 低（计数器可见） |
| 任务连贯性 | 依赖模型回忆 | TODO 外部记忆 |
| 错误修复 | 盲目重试 | 有修复建议 |
| 平台决策 | 不知道 OS / Shell | 明确注入系统状态 |

### 结论

上下文不是简单地把聊天记录堆进去。好的 Agent 框架会把**时间、工具调用次数、任务进度、错误诊断、环境状态**等隐式信息，组织成显式状态栏注入上下文。这直接决定了模型「能看到什么」，也就决定了它「能做出什么决策」。

### 一句话总结

> 上下文工程的核心是：把模型需要的信息，以正确的方式、在正确的位置、以正确的粒度组织好，让模型在每个决策点都能看到足够且不冗余的信息。
